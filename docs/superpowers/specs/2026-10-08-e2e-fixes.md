## 2. 逐缺陷条目

### BUG-01【high · verified · fix】HLS 分片解析为无效 blob: URL 永不起播且静默；.ts 被按代码渲染乱码

**现象**（报告 §5 BUG-01，对应场景 MEDIA-04）：m3u8 播放列表正常加载（duration=6 已解析）但分片请求全部指向无效 `blob:http://host/seg0.ts` 并反复 XHR 重试，readyState 恒 0，无任何错误提示；video.ts 直接进 vv-code 容器渲染 MPEG-TS 乱码；flv 正常（对照）。

**根因**（【代码确证】）：

1. m3u8：`packages/render-media/src/av.ts:161` 把**整份 m3u8 文本包成 blob URL**（`URL.createObjectURL(makeBlob())`），`makeHlsLoader`（av.ts:80-93）`hls.loadSource(blobUrl)` 后 hls.js 以该 blob URL 为 base 解析相对分片名 → `blob:.../seg0.ts` 不存在 → 无限重试。分片不可达时 hls.js 的 ERROR 事件无人订阅，loader 失败仅有 `notifyLoaderFailure`（av.ts:70-77）覆盖 import/构造失败，不覆盖运行期分片错误 → 静默。
2. .ts：`avRenderer.extensions`（av.ts:123）刻意不注册 `ts`（注释 av.ts:124-125：codeRenderer 先占，registry 重复注册抛错，见 `packages/core/src/registry/registry.ts:26-28`）→ `det.ext==='ts'` 走 `byExtension('ts')` 命中 codeRenderer（`packages/render-text/src/code.ts:559` extensions 含 'ts'）→ 二进制当 TypeScript 文本渲染。dispatcher 只按扩展名选路（`packages/core/src/dispatch/dispatcher.ts:19-21`），`sniffSignature`（`packages/core/src/detect/magic.ts:7-15`）也没有 MPEG-TS 签名（0x47 同步字节），无任何内容纠偏路径。

**修复方案概述**：

1. HLS 直连真实 URL：remote store 的 m3u8 不再包 blob，构造 `/api/file?path=<m3u8 路径>` 直连 URL 交给 `hls.loadSource`，分片相对路径由 hls.js 按真实 URL 解析；token 鉴权经 hls.js `xhrSetup`（或 fetchSetup）附加 `Authorization: Bearer`。本地 store（无服务端 path）实现自定义 loader（pLoader）：分片名在同目录 `store.listChildren` 解析、经 `store.read` 生成短命 blob 喂给 hls.js；实现不了的分片在错误卡片明示。若改造范围过大，可先落 remote store 直连 + 本地 store 报「本地 HLS 暂不支持」的明确错误，二者都必须消除静默。
2. 错误呈现：`makeHlsLoader` 内订阅 `Hls.Events.ERROR`（fatal → 通知/错误卡片），mpegts 同理订阅 player 错误事件；分片 404 等不可达场景给出可理解文案，杜绝无限重试（设置重试上限后转错误卡片）。
3. .ts 播放路径：`sniffSignature` 增加 MPEG-TS 识别（head[0]==0x47 && head[188]==0x47 && head[376]==0x47，三重同步字节判定，TypeScript 文本不会命中）；dispatcher 在「扩展名命中 code 渲染器且 signature==='mpegts'」时改派 av 渲染器（复用既有 sniff 改派机制 dispatcher.ts:23-30）；同时把 `'ts'` 加入 av.ts `VIDEO_EXTS`（av.ts:29，否则改派后 playerKindOf 会落 audio 分支）。

**验收标准**（场景 MEDIA-04）：

1. 打开 video-hls.m3u8：分片请求 URL 以可达地址开头（非 `blob:`），10s 内 readyState≥3、currentTime 推进、可播完；网络面板无同一分片 >3 次的重复请求。
2. 打开 missing-seg.m3u8：≤10s 内出现明确错误提示（错误卡片或播放器内错误文案），无静默挂起。
3. 打开 video.ts：挂载的是视频播放器（hasVideo=true），readyState≥3，不出现 vv-code 容器；TypeScript 源码文件（samples/m2/sample.ts 等）仍走 code 渲染器正常高亮（回归护栏）。
4. 打开 video.flv：readyState=4、可播完（回归护栏，现状不得回退）。

**影响面与风险**：av.ts 为媒体主路径（mp4/flv/mp3 共用），改造需保留现有 blob 生命周期管理（av.ts:5-8 注释的零泄漏约束）；hls.js/mpegts.js 为可选依赖动态 import，直连 URL 的鉴权头注入需覆盖 token 为空场景；MPEG-TS 嗅探误判风险低（三重 0x47 校验）但需对 .ts 文本样本回归（HL 域 sample.ts）。

### BUG-02【medium · verified · fix】btrfs 数据根 watcher 持续 watch-error，自动刷新不可用且无自愈

**现象**（报告 §5 BUG-02，对应场景 SRV-06）：8391（btrfs /dev/sda3 数据根）任何写入仅推 `{"type":"watch-error"}`，状态栏常驻「自动刷新不可用」（建连即出现），tab 永不自动重读；同 release 二进制在 tmpfs 对照实例全链路正常（append 后 3s 自动重读、scrollTop 保留）。

**根因**（【代码确证】自愈缺失部分；【待验证】btrfs 触发条件）：

1. watcher 启动失败被静默吞掉：`server/src/watch.rs:41-47` `recommended_watcher(...).ok()` + `w.watch(root, Recursive).ok()` 两步 `ok()` 把 Err（含 OS 错误码）直接丢弃，无任何日志；失败则 `watcher_ok=false`（watch.rs:59-63），此后**每个 SSE 连接**建连即收到一条降级帧（`server/src/routes/events.rs:49-57`）——与报告「SSE 建连时即出现自动刷新不可用」吻合。
2. 运行期无自愈：`debounce_loop`（watch.rs:76-121）首个 Err 即置 `errored=true`，透传一条 watch-error 后**永久静默**（watch.rs:83-90），不重试、不重建 watcher。
3. 【待验证】btrfs 上触发启动失败/运行期错误的直接原因未定位（报告 §7.1 第 4 项明示未覆盖）：候选为 inotify watch 上限（fs.inotify.max_user_watches ENOSPC）、notify 对 btrfs 子卷/挂载拓扑的递归建 watch 失败、或内核 btrfs+inotify 兼容性问题。`.temp/e2e-server.log`（若仍存）与在 btrfs/ext4/xfs 上以最小 Rust 探针复跑 `notify::recommended_watcher` 可定论。

**修复方案概述**：

1. 启动路径：watch.rs 保留 Err 原因并写 stderr 日志（含 OS 错误码与 root 路径）；启动失败带退避重试（如 3 次）。
2. 运行期自愈（**含所有权重构，按重构任务预估而非局部小改**）：现状 `debounce_loop` 聚合线程仅持有 mpsc receiver（watch.rs:52 只移入 `raw_rx`），watcher 句柄留在 `ChangeHub._watcher`（watch.rs:30/55）——循环内直接重试 `watch(root, Recursive)` 或换 `PollWatcher` 均拿不到句柄。需二选一重构：a) 把 watcher 句柄（或重建 watcher 的工厂闭包）传入聚合线程，Err 时在循环内重建；b) Err 时新建 watcher + 新 channel，聚合线程双路接收后切换。重试仍失败则降级 `notify::PollWatcher`（轮询，跨文件系统可用）继续广播 changed；全程状态经 `ChangeHub` 暴露（watcher_ok 语义细化为 ok/degraded/recovering），前端已有 watch-error 处理（`packages/core/src/tree/remote.ts:142-149`），可加一条恢复提示帧（未知 type 前端天然忽略，向后安全，events.rs:77-79 已留此惯例）。
3. 诊断补丁随修复提交：`--root` 启动时打印文件系统类型与 watcher 后端（便于 e2e 环境判读）。

**验收标准**（场景 SRV-06）：

1. 在 btrfs 数据根实例：SSE 建连后无 watch-error 帧（或先 watch-error 后出现 recovered 提示且此后不再降级）；服务器侧 append 后 ≤3s tab 自动重读新行、scrollTop 保留；`curl -sN /api/events?ticket=…` 观察到 `{"type":"changed","paths":[…]}`。
2. 人为制造 watcher 故障（如临时 max_user_watches 压到极小或改 root 权限）：服务器日志出现含 OS 错误码的明确日志；恢复条件移除后（或降级 PollWatcher 后）写入重新产生 changed 帧（自愈可测）。
3. tmpfs/ext4 对照实例回归不回退（现状 SRV-06 tmpfs 全链路 ✓ 保持）。

**影响面与风险**：watch.rs 全同步线程模型（watch.rs:8-9 注释）需保持（AppState 无 tokio runtime 构造约束）；PollWatcher 的轮询间隔需权衡 CPU（建议 ≥2s）；前端无需改动（changed 帧协议不变）。

### BUG-03【medium · verified · fix】spec 5.11 键盘快捷键 j/k/gg/G/Ctrl+P 全部零实现

**现象**（报告 §5 BUG-03，对应场景 SHELL-11）：trusted keydown 全部到达 window（探针证实）但代码区 scrollTop 恒 0、无快速打开面板；`/` 正常，eval 赋 scrollTop 生效——监听链路有效、纯无实现。

3. 快捷键不与 `/`、Ctrl+Shift+F、Esc、TabBar 既有键冲突；输入焦点不接管。

**验收标准**（场景 SHELL-11）：打开 301 行 long-code.js 后：按 j×43 后 `.vv-code-pre.scrollTop` ≈ 860（43×20）；按 k 回滚；g g 后 scrollTop=0；**G 后断言 `scrollTop === scrollHeight - clientHeight`（跳到底，不写死具体数值——报告口径 ≈5567 依赖 e2e 视口 clientHeight，换视口即漂移，不作断言）**；Ctrl+P 弹出面板、输入 long 选中 long-code.js 回车后该 tab 激活；焦点在输入框时按 j/k 不滚动（inField 守卫）；`/` 与 Ctrl+Shift+F 回归不回退。

**影响面与风险**：全局键位与既有 `/`、Ctrl+Shift+F 的 inField 语义必须一致，否则输入框误触发；gg 序列需限时（如 500ms 内两击）避免 g 单键误触；虚拟滚动容器 scrollTop 写入已有成熟路径（gotoMatch，code.ts:534-548）。

### BUG-04【medium · verified · fix】状态栏编码/语言/大小/行列元数据整体未渲染（服务端 x-vv-* 头已正确下发）

**现象**（报告 §5 BUG-04，合并 SHELL-12+HL-06+HL-07+SRV-05）：代码文件状态栏仅「高亮: … · 执行: … · 自动刷新不可用」，outerHTML 中编码/语言/大小/行列四字段均为 Svelte 条件占位；curl 证实 x-vv-lang/x-vv-encoding 正确下发（Range 206 同样携带）。

**根因**（【代码确证】）：状态栏模板只有三个段——engineLabel、watchHealth、statusNotice（`apps/web/src/lib/ViewerPane.svelte:193-197`），四字段从未实现；数据其实已在前端：编码/语言在 `getRemoteMeta`（`packages/core/src/tree/remote.ts:250-261` 读头写入，`code.ts:568` 已消费用于解码/高亮），大小=buffer.byteLength、行数=code 实例 `lines.length`（`code.ts:352`，注意 `buildLineIndex` 为 `text.split('\n')`：以 `\n` 结尾的 301 行文件实测产出 **302 个元素**（末元素空串）——行数字段必须按内容行数口径计算，见修复方案），但渲染实例未暴露、ViewerPane 不可得；MetaPanel 仍是占位（`apps/web/src/lib/MetaPanel.svelte:8`「文件元数据（M4 接入）」）；本地文件的 det.encoding 在 Detection 中已有但同样未出口。

**修复方案概述**：

1. 渲染实例侧：code 渲染器 handle 增加 `getMeta(): { encoding?: string; lang?: string; size: number; lines: number }`（encoding/lang 从 opts/meta 取，size=buffer.byteLength；**lines 按内容行数口径：`lines[lines.length-1] === ''` 时取 `lines.length - 1`，否则 `lines.length`**——与 `wc -l` 一致，避免「301 行文件显示 302」）；image/av/pdf/archive 等渲染器至少暴露 `getMeta(): { size: number }`（buffer.length 均在手）。
2. ViewerPane：engineTimer 轮询处一并读 meta，状态栏新增「编码: … · 语言: … · 大小: … · 行: …」段（仅 code 显示行列；媒体/图片显示大小与编码）。
3. MetaPanel 同步展示同源元数据（顺带兑付 M4 占位，规模可控：名称/大小/编码/语言/来源 store）。

**验收标准**（场景 SHELL-12、HL-06、HL-07、SRV-05）：打开 long-code.js（`.temp/e2e-data/domain-app-shell-sources/long-code.js`，实测 `wc -l`=301、以 `\n` 结尾）：状态栏含「语言: javascript · 编码: utf-8 · 大小: 10816 · 行: 301」——**行数断言为 301（内容行数口径），若显示 302 即实现未按本 spec 口径，判不通过**；打开 GB18030/UTF-16LE/UTF-8 BOM 件：编码段分别显示 gb18030/utf-16le/utf-8（与服务端 x-vv-encoding 逐字一致，`curl -I` 对照）；打开 pixel.png 与 sample.mp4：状态栏至少含大小与编码；`.vv-statusbar` outerHTML 不再出现空占位注释。

**影响面与风险**：RenderedInstance 接口扩展为可选方法（`'getMeta' in inst` 探测），不改 core 类型强约束；错误卡片实例无 meta（显示为空段即可）；行列仅对 code 有意义，markdown 渲染视图不显示行列（无行概念）。

### BUG-05【medium · verified · fix】设置面板整体缺失：排除规则/自动刷新开关/手动刷新按钮无 UI 入口

**现象**（报告 §5 BUG-05，合并 SHELL-09+SHELL-13+SRV-07）：全页面穷举无设置/排除/刷新控件；排除引擎与持久化经 localStorage 探针验证正常；追加内容后用户无任何 UI 手段刷新。

**根因**（【代码确证】）：Settings 数据模型字段齐备（`apps/web/src/lib/stores/settings.ts:8-9` excludedPatterns/autoRefresh）且 FileTree 已消费 excludedPatterns（`AppShell.svelte:133`），但 TopBar 只有打开/URL/连接服务器/主题/计算策略/代码主题（`TopBar.svelte:115-166`），无设置面板组件；刷新只有 SSE 被动通道（`openFlow.svelte.ts:108-114` refreshPaths 由 store.watch 驱动），无用户触发入口。

**修复方案概述**：

1. TopBar 加「设置」（或 ⚙）按钮 → SettingsPanel 浮层（对齐连接服务器内联表单模式）：排除规则编辑（条目列表 + 预设 .git/node_modules 一键加入）、自动刷新开/关（autoRefresh）、刷新模式说明；写经 `saveSettings`（settings.ts:43-45，持久化免费）。AppShell 响应式读 settings，FileTree 已按 excludedPatterns 过滤，改动只在 UI 层。
2. 手动刷新按钮（TopBar ↻ 或状态栏）：对活动文件 tab 调 `tabStore.refreshPaths(store.source.storeId, [tab.source.path])` 强制 `rev++`（openFlow.svelte.ts:108-114 既有通道）触发重读；autoRefresh=false 时 SSE listener 不自增 rev（openFlow.svelte.ts:332-338 处按设置过滤）。

### BUG-13【medium · verified · fix】zip 改名 .txt 后无 magic 预检重定向，按 code 渲染二进制乱码

**现象**（报告 §5 BUG-13，对应场景 BIN-10）：zip-as-txt.txt 树点击后以 code 渲染器显示 zip 原始字节乱码，两入口均无 magic 探测（网络层仅 4 次 GET /api/file，无探测请求）。

**根因**（【代码确证】）：`sniffSignature` 已识别 zip 签名（`magic.ts:8`，detect/index.ts:15 记入 `det.signature`），但 dispatcher 只按扩展名选路、且只调用**当前命中渲染器自己的** sniff（dispatcher.ts:19-30）；archive 渲染器的 magic 分派在其 render 内部（`archive.ts:38-41,123-125`），对 .txt 扩展名根本不会被选中；code 渲染器无 sniff → 无任何纠偏。ooxml 渲染器 sniff 永不改派（`render-doc/src/ooxml.ts:23-28`，设计裁决）。

**验收标准**（场景 BIN-10；「只重定向一次」的验证样本按本节裁决口径选文本类扩展名，与 `docs/e2e/binary-hex-archive.md` BIN-10 预留的「修复后需按实现明确」口子一致）：

1. 树点击 zip-as-txt.txt 与 URL 入口打开：均进入压缩包渲染器并展示包内条目树（hello.txt 等条目与 unzip -l 一致）——「.txt（文本类）+ zip 签名」正向改派。
2. 只改派一次（反向样本按裁决口径）：`.txt` 扩展名 + PDF 签名（`head -c 200 样本.pdf` 拼接文本尾部构造）→ 改派 pdf 渲染器后不再二次改派；`png` 内容拼文本尾部的 `.txt` 样本 → 改派 image 渲染器一次。**.zip 扩展名 + PNG 签名的反向样本不改派**：期望仍走 archive 渲染器并以「无法识别的压缩包格式」错误卡片呈现（不进 image、不出 code 乱码）——该口径验证的是「内容确实不是 zip」的正确错误呈现，而非改派。
3. 回归：正常命名 zip/txt/docx 不变（BIN-01~07、MD 域 .txt 渲染、MEDIA-08 docx 均不回退）；正常命名 zip 优先经 jszip 路径（isZipMagic 命中），仅伪 zip 落 libarchive 错误卡片。

**影响面与风险**：改派面覆盖所有文本扩展名 + 已识别签名组合，需对「假 zip 头的文本」极小概率误派做说明（签名为强特征，风险可忽略）；BUG-07 的无扩展名回退链复用同一签名表（实现时合并为一个 `signatureRedirect(det)` 纯函数，core 可单测）。
